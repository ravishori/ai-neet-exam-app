## 4. Constrained-retrieval diagnostics (same-subject and same-subject+chapter)

Run entirely in-memory against the live DB-loaded KU index; no persistent state touched.

| Configuration | Population | Covered (relaxed 0.25) | Coverage % |
|---|---|---:|---:|
| Unrestricted (full pending population) | 9,944 | 8,159 | 82.1% (reproduces prior audit) |
| Unrestricted, labeled-subject questions only | 4,346 | 3,710 | 85.4% |
| **Same-subject-constrained** | 4,346 | **2,449** | **56.4%** |
| Same-subject-and-chapter-constrained | *(could not be run as specified — see below)* | — | — |

**1,261 questions (of the 4,346 labeled population) lose their only match when retrieval is constrained to the question's own labeled subject** — this is the concrete, measured count of `false_negative_candidates` the task asked for: real matches the unrestricted matcher found that a subject filter would discard. Whether those 1,261 lost matches were themselves correct or incorrect is unknown without human review; this number quantifies the risk/benefit tradeoff, not the correctness of either side.

**Same-subject-and-chapter-constrained retrieval could not be run as literally specified.** `pyq.questions` carries no chapter or topic label at all — `class_level` and `concept_id` are 100% NULL across all 12,396 rows (directly confirmed, consistent with the original 2026-10-01 baseline audit). There is no question-side chapter metadata to constrain against. Reported honestly as not performed, rather than substituting the *matched unit's own* chapter as a stand-in filter, which would be circular (it would trivially always match, since it's filtering by the very thing being matched).

**Interpretation:** same-subject constraint alone would cut unrestricted-relaxed coverage among labeled questions from 85.4% to 56.4% — a substantial reduction, consistent with the prior audit's 55.4% cross-subject-mismatch finding being a real, large-magnitude phenomenon rather than noise. This is presented as a **measured tradeoff**, not a recommendation — adopting a subject constraint would need the same human-review validation as any other threshold or filter change before being trusted.

## 5. Zero-significant-word questions (the 42) — investigated

File: `docs/quality/_retrieval_human_review_2026-10-01/zero_significant_word_analysis.csv` — all 42 rows, including full stem text, stem/options significant-word counts, and a `candidate_query_representation` (the union of significant words found in stem + options, for potential future query construction — **not used to change any live retrieval behavior**).

| Mechanism | Count |
|---|---:|
| Stem and options both lack significant terms | 32 |
| Options contain scientific terms the stem doesn't | 10 |

**New, concrete finding from reading the actual text (not available in the prior audit, which only had aggregate counts):** inspecting the raw stem text directly reveals that a meaningful share of this group is not "genuinely content-free" — it is **visibly corrupted/garbled PDF extraction output**. Examples, verbatim from the database:

- `"2p, <(z 2p, =\" 2p, )<o 2p,"` — almost certainly a mangled electron-configuration notation (subscripts/superscripts lost or scrambled during extraction)
- `"hat is th le of RNA pol Il i"` — visibly truncated/corrupted ("What is the role of RNA Pol II"), losing exactly the significant words ("role", "RNA", "polymerase") that would have made this question matchable
- `"Bi hs I and S i"`, `"mH 3 �102 41\n7 our\n320 V, 50 Hz"` — similarly corrupted

This points to a **PDF text-extraction quality problem specific to this subset**, not a retrieval-matching limitation and not a missing-source problem. It is distinct from, and in addition to, the already-documented lack of symbol/subscript/superscript handling in the word-tokenizer (prior audit, Section 4) — here the underlying extracted text itself appears damaged, which no amount of tokenizer improvement could fix. **This is reported as an observed pattern in a manual read of the 42 rows, not a systematically quantified count** (no automated garbling-detection heuristic was built or validated) — a rough manual scan suggests roughly a third to just over a third of the 42 show visible corruption, but this is not a precise, reproducible metric and should not be cited as one.

**10 questions have scientific terms in `raw_options` that are entirely absent from the stem** — e.g. option values containing chemistry/physics notation while the stem text is empty of significant words. This confirms the task's hypothesis: the current matcher's exclusive reliance on `raw_stem` is a real, structural gap for this subgroup, independent of threshold choice. **No change to the actual retrieval query was made** — this is reported as a finding for a future, separately-scoped code change.

## 6. Zero-overlap questions (the 113) — traced

File: `docs/quality/_retrieval_human_review_2026-10-01/zero_overlap_tracing.csv` — all 113 rows.

For each question, this audit checked (deterministically, without reading the question's actual topic): whether it carries a `subject` label, and whether that subject has *any* ingested knowledge units at all (a minimal sanity check — if a subject has zero ingested content of any kind, mechanical overlap is structurally impossible; if it has content, zero overlap is a vocabulary/relevance question that can't be resolved without reading the question).

**Result: all 113 are classified `UNRESOLVED`.** Every subject appearing among these 113 questions does have at least some ingested knowledge units — there is no case where "this subject has zero source material ingested" explains the zero overlap. That rules out the most severe possible cause (`TAXONOMY_OR_METADATA_GAP` in the strict sense of "subject completely unmapped") for every one of the 113, but it does **not** establish that relevant content exists for any specific one of them — doing so requires reading each question individually, which this audit's deterministic tooling cannot do. Per the task's explicit instruction, **no conclusion that source material is missing is drawn from zero lexical overlap alone**, and no row is force-classified into a more specific bucket without that individual evidence.

## 7. Human-review rubric

To be used by a reviewer with the `reviewer_worksheet.csv` columns `question_text`, `question_options`, `candidate_passage_full`, `source_document`, `source_page` visible (no answer key is present in the file):

| Label | Definition |
|---|---|
| `RELEVANT` | The candidate passage directly supports the scientific concept the question is actually asking about — a student could use this passage alone to understand what's being tested, even if it doesn't state the final answer outright. |
| `PARTIALLY_RELEVANT` | The passage is topically related (same chapter/concept area) but doesn't provide enough specific detail to resolve the question on its own — e.g. it names the right phenomenon but not the specific fact being tested. |
| `IRRELEVANT` | The passage does not substantively relate to what the question is asking, even if it shares surface vocabulary with the stem (this is the label most likely to apply to the cross-subject and generic-vocabulary matches flagged in Section 3). |
| `INSUFFICIENT_SOURCE` | The passage is too short, fragmentary, or provenance-incomplete to make a confident judgment either way (e.g., a one-sentence `structured_fact` with no surrounding context). |
| `UNRESOLVED` | The reviewer genuinely cannot decide — use this rather than guessing; do not leave the field blank once review has started (a blank field means "not yet reviewed", not "reviewed as unresolved"). |

**Disagreement handling (recommended, not yet operationalized):** if more than one reviewer labels the same row, treat any `RELEVANT` vs. `IRRELEVANT` disagreement as requiring adjudication by a third reviewer or the project owner before the row counts toward a precision estimate; `PARTIALLY_RELEVANT` vs `RELEVANT`/`IRRELEVANT` disagreements can be resolved by simple majority. **Sampling for adjudication:** if resources allow only partial adjudication, prioritize disagreements in the highest-volume cross-subject pairs (Section 3) and in the 0.40–0.49 score band, since those carry the most weight in any future threshold decision.
